大家好，我是EthanYuan。

最近我寻思着，AI应用开发岗位数量贼多，正好自己不想局限于Java开发，想做一个复合型人才大学生程序员，于是计划自己**手搓**一个能用的智能体应用出来。正好，我那个跟着课程学、自己换皮改造的SpringBoot项目——《昴云相册》，成了我最好的“试验田”。

**为啥非要做这个？** 说来也简单，就是被朋友一句话给刺激到了。朋友看了我的图库，吐槽说：“你这玩意儿，传图靠手填、搜图靠缘分，连个AI的影子都没有，是上个世纪的古董吧？”

我当场就不服气了。嘿，你说我项目写得不行可以，但说我没跟上时代？这不能忍。

于是，**2026年6月9日**，我新建了一个文件夹。接下来的20天，我彻底陷入了“对AI提需求→被AI虐→含泪优化→再提需求”的无限循环里。今天，我就来复盘一下，这20天我是怎么从一个普通后端，被逼着“手搓”出一个智能体应用的。这篇文章全是干货和血泪，建议先收藏再看。

### 一、最初的想法：我是怎么被“逼上梁山”的？
一切的开端，都是因为原来的云图库项目，有几个痛点实在太“痛”了，痛到我每次用都想给自己两拳。

+ **痛点一：人工审核，慢到怀疑人生**。用户传完图，得等管理员上班才能审核。要是半夜传图，黄花菜都凉了。并发一高，人工根本审不过来，用户就卡在“待审核”状态干瞪眼。
+ **痛点二：上传图片，比写周报还累**。名称、简介、分类、标签……一张图填一堆字段。批量上传更是“灾难”，那个批量命名功能死板得像个木头，根本解决不了实际问题。
+ **痛点三：搜索功能，约等于“猜字谜”**。后端用了个简单的模糊查询，用户必须**一字不差**地输入关键词。什么“以图搜图”、“语义搜图”？不存在的，搜不到就是搜不到，体验极差。

看着这几个痛点，我脑子里突然冒出一个声音：**“怎么不把AI用上？”**

既然市面上有那么多AI能力，我为什么不给这个“古董”项目，装上一个**智能大脑**呢？说干就干，我立刻开始构思，这个智能体到底要长啥样。

### 二、蓝图构想：我的智能体得会这“十八般武艺”
在动手之前，我花了一天时间，把自己想象成一个产品经理，列出了“昴云智能体”必须拿下的能力清单：

1. 📷 **自然语言图片检索**：能用大白话找图。比如，输入“**找一张黑发女孩、戴着红色圣诞帽的照片**”，它就能给我翻出来。
2. 💬 **智能对话式筛选**：记性得好。能记住我之前说过“我喜欢动漫风”，下次再问时，它就能优先推荐动漫相关的图片。
3. **❓ 图片内容理解**：得长“眼睛”。能看懂图里是风景、人物还是猫猫狗狗，甚至能分析出图片的风格和情绪。
4. **💗个性化推荐**：得会“猜你喜欢”。根据我当前看的图，能推荐“你可能还喜欢这些...”。
5. **🌍 智能化图片上传**：能帮人“偷懒”。我丢给它一张图和一句话“这是一张我在海边拍的落日”，它就能自动帮我填好所有标题、分类和标签。
6. **🔍AI自动审核**：能当“7x24小时保安”。图片一上传，AI立马审核，合规的秒过，再也不用人盯着了。

看到这，你可能觉得“哇，功能真多”。但对我来说，**真正的挑战才刚刚开始**。从构想到落地，技术选型才是第一道坎。

### 三、技术选型：从“一头雾水”到“组合拳出击”
功能定好了，用什么工具来造呢？

#### 1. AI开发框架：为什么我选了“LangChain + LangGraph”组合？
现在AI开发框架多如牛毛，挑花眼。我一开始用**LangChain**快速做了个AI导游的Demo，觉得真香。但一应用到云图库这个复杂场景，就发现问题了。

智能体需要先判断用户意图，然后走不同的分支，比如“搜索”走A路，“上传”走B路，“闲聊”走C路。**用LangChain传统的链式结构来写这种多分支逻辑，代码会变得一团乱麻，像意大利面条一样，牵一发而动全身。**

后来我发现了 **LangGraph**。好家伙，这就是我要的！它用“图”的方式管理状态，**把“意图识别-分支路由-调用工具”这些步骤，变成一个个清晰的“节点”和“边”**。整个流程像一张地图一样直观，代码结构瞬间清爽了。

**最终方案**：用**LangGraph作为工作流引擎**，处理复杂逻辑。用**LangChain作为工具箱**，只拿它好用的部分，比如提示词模板（`ChatPromptTemplate`）、文档加载器等。**各取所长，完美配合。**

> **一个小技巧**：我在设计工作流时，会先用可视化工具 **Dify** 画一遍流程图，确认无误后，直接截图给AI编程工具，让它照着图生成代码框架，效率直接起飞。
>

#### 2. 记忆持久化：为什么Redis是“天选之子”？
智能体要能记住对话，不然就是“鱼的记忆”。我考虑了三种方案：

+ **内存**：服务一重启，记忆全丢，生产环境用这个就是“自杀”。
+ **数据库（MySQL）**：每次都查库，高并发下IO压力太大，响应慢。
+ **Redis**：基于内存，速度快，支持数据过期（TTL），重启数据不丢，最关键的是，**LangGraph的**`RedisSaver`**能直接对接**，几行代码就搞定会话持久化，香得不行。

结论：**Redis，就你了！**

#### 3. 多模态RAG检索：三层架构，让AI真正“看懂”图片
这是整个应用最核心、也最复杂的一块。为了兼顾**精确筛选**（比如“标签是‘风景’”）和**语义理解**（比如“一张让人感到平静的海边日落图”），我设计了**三层检索架构**：

+ **第一层：意图路由与查询改写**。先判断用户是想“精确查找”还是“模糊描述”。如果是模糊描述，就先用大模型提取关键词和过滤条件（时间、分类等）。
+ **第二层：向量召回 + 元信息过滤**。这是核心。我用 `qwen3-vl-embedding` 多模态模型，把**图片的“名称+简介”和图片本身**融合成一个“特征向量”存到向量库 **Chroma** 里。搜索时，用户的描述也会转成向量，去库里找最相似的。同时，元信息（如标签、分类）作为**过滤条件**，帮我们圈定一个更小的范围，让搜索更准。
+ **第三层：多模态重排序**。向量召回的结果可能不够精准。我再调用 `qwen3-vl-rerank` 重排序模型，对Top-20的结果重新打分排序，把最符合意图的图片排在最前面。

这套组合拳下来，搜索精度有了质的飞跃。既利用了向量的语义能力，又保留了传统过滤的精确性。

#### 4. 后端服务化：为什么选FastAPI？
智能体应用开发完了，怎么和我的Spring Boot项目以及前端沟通呢？我选了 **FastAPI**。

理由很直接：

+ **Python AI 生态的天然搭档**：LangChain、Chroma等全是Python生态，用FastAPI无缝衔接。
+ **快速微服务化**：它能轻松地把AI能力包装成一个个RESTful API，供主项目调用，完美解耦。
+ **性能和部署友好**：异步支持、自动生成API文档（Swagger），配合Docker部署非常丝滑。

#### 5. 项目上线：Docker Compose，一键拯救世界
部署环节，我直接放弃了以前在宝塔面板上手动配环境的“原始人”方式，拥抱了 **Docker Compose**。一个 `docker-compose.yml` 文件，就把前端、后端、AI微服务、Redis、MySQL、RabbitMQ全部搞定，**一条命令，全部拉起，世界清净了**。

当然，过程也不是一帆风顺。我在构建AI微服务镜像时，遇到了一个巨坑：**基础镜像里的Redis依赖版本太低**，导致程序启动报错，排查了整整一天才找到问题。这个辛酸史，我打算之后单独写一篇“踩坑记”来详聊。

### 四、一些小尝试
在做 Function Calling 时，我定义了两个工具：一个是用LangChain自带的**Tavily搜索工具**，另一个是调用第三方API的**动漫分析工具**。这让智能体不仅能看图，还能根据需求去查外部知识。

至于 **MCP**，虽然当前业务还没用上，但我已经把所有配置都封装好了。我甚至用 **Bing MCP** 测试过，能跑通。为的就是以后新功能一来，能立刻接入，保持技术的前瞻性。
